# Live verification

What has been run against a real CloudPanel, and on which release. Everything not listed here has only run against the `clpctl` simulator
(`test/sim`), whose grammar comes from the official documentation and from outputs recorded below.

| CloudPanel | What ran | Result |
| ---------- | -------- | ------ |
| 2.5.4 | `clpctl` (usage listing), `vhost-templates:list`, `user:list` (read-only, over SSH, no terminal) | recorded in `test/fixtures/recorded`: 28 commands listed; no `varnish-cache:purge` in the root listing; `system:permissions:reset` is listed |
| 2.5.4 | the `read` family of `scripts/contract-test.mjs` through the built server over SSH with `sudo -n`: server info, the command listing compared with the documented set, `user:list`, `vhost-templates:list`, `vhost-template:view --name=Generic`; nothing created or changed | 7 checks passed: 28 commands detected, none of the documented commands missing, no option differences, both tables parsed, the template `Generic` viewed |
| 2.5.4 | the `static` and `proxy` families of `scripts/contract-test.mjs` through the built server over SSH with `sudo -n`: `clp_site_add_static`, `clp_site_add_reverse_proxy` (upstream on a local port), each followed by `clp_site_delete`, with throwaway names | 4 calls and 2 cleanup checks passed: both sites were created and deleted (exit 0), no throwaway panel user or template left |
| 2.5.4 | the `php` and `nodejs` families: `clp_site_add_php` (PHP 8.3, template Generic), `clp_site_add_nodejs` (Node 20), each followed by `clp_site_delete`, throwaway names | passed. Observed: CloudPanel itself refuses an application port another site already uses ("port: Port is already in use") and creates nothing (checked: no leftover user or vhost); the script then takes another port (`--node-port`, `--python-port`). |
| 2.5.4 | the `python` and `database` families: `clp_site_add_python` (Python 3.12), then on a throwaway static site `clp_db_add`, `clp_db_export` and `clp_db_import` with absolute paths in `<fileDir>/dumps/`, `clp_db_delete`, `clp_site_delete`; file directory in the SSH account's home (`allowUntrustedFileDirs`) | passed: 10 calls and 4 cleanup checks (the dump file and the directories the run made were removed). A file directory under `/var/lib` needs to be created by root first; the script cannot do it as a non-root account. |
| 2.5.4 | the `certificate` and `template` families: a self-signed certificate generated locally, copied to `<fileDir>/certs/` and installed with `clp_site_install_certificate` on a throwaway static site; `clp_vhost_template_add` (from `<fileDir>/templates/`), `clp_vhost_template_view`, the template in `clp_vhost_templates_list`, `clp_vhost_template_delete` | passed. Observed: `vhost-template:add` reads its file as CloudPanel's own account, not as root: a `0600` file in a `0750` home was answered with "Vhost Template cannot be empty"; with `templates/` `0755` and the file `0644` it worked. `site:install:certificate` read `0600` key files in a private directory fine (it reads as root). |
| 2.5.4 | the `user` family: a throwaway static site, `clp_user_add` (role user, that one site), `clp_user_list`, `clp_user_reset_password`, `clp_user_disable_mfa`, `clp_user_delete`, `clp_site_delete` | passed on the second run. **The first run found a bug:** `clpctl user:delete` without `--force` asks "Confirm to delete the user: X (yes/no):", gets no answer (no terminal) and exits 0 having deleted nothing, so the tool reported success and the user stayed (the one left by that run was removed by hand with `--force`). `clp_user_delete` now passes `--force` and treats an unanswered yes/no question as a failure. |
| 2.5.4 | `clp_cloudflare_update_ips`, `clp_vhost_templates_import` (both contact the internet), `clp_db_show_master_credentials` (the output was saved to a private local file, nothing shown, the file deleted afterwards) | passed (3 calls, exit 0). Nothing was deleted or changed in what existed before; no password was changed. |

Not run against a real server, on purpose: `clp_cloudpanel_enable_basic_auth` / `clp_cloudpanel_disable_basic_auth` (they change who can reach the panel; a failed second step would lock the operator out), `clp_cloudpanel_set_release_channel`, and the two site-user commands (they need an SSH login as a site user). They have only run against the simulator.

The tool families (sites of the five types, certificates, databases, users, vhost templates, the panel switches, the site-user commands, the inventory script)
are verified one at a time by a maintainer, with throwaway names and a before/after comparison, and added to the table above.
